# OpenSSF Best Practices Self-Assessment

Criterion-by-criterion self-assessment of this repository against the
[OpenSSF Best Practices badge](https://www.bestpractices.dev/) **passing**
level (67 criteria), audited on 2026-08-10 against the canonical criteria
source (`coreinfrastructure/best-practices-badge`, criteria level 0).
Each entry below is written as a questionnaire-ready justification with its
evidence link, so the badge entry can be completed by transcription once the
project is registered.

## Summary

| Group | Met | N/A | Unmet |
|---|---|---|---|
| Basics | 10 | 1 | 2 |
| Change control | 8 | 1 | 0 |
| Reporting | 7 | 1 | 0 |
| Quality | 12 | 0 | 1 |
| Security | 7 | 9 | 0 |
| Analysis | 7 | 1 | 0 |
| **Total** | **51** | **13** | **3** |

All three remaining Unmet criteria trace to a single pending owner decision —
the repository license:

- **floss_license** (MUST) and **floss_license_osi** (SUGGESTED): the
  top-level LICENSE is proprietary. The badge requires the released results
  to be FLOSS via any one of four routes (OSI, FSF, Debian main, Fedora).
  CC-BY-4.0 qualifies for the documentation content via the FSF, Debian,
  and Fedora routes; Apache-2.0 or MIT qualifies for the tooling.
- **test** (MUST): the automated gate exists and runs on every change, but
  the custom validators under `scripts/` are covered by the proprietary
  license, so the suite is not “released as FLOSS”. The minimal fix is
  dual-licensing `scripts/` (e.g. MIT) without relicensing the corpus.
- **tests_documented_added** (SUGGESTED): resolved — the validator-extension
  policy is now documented in CONTRIBUTING.md and the pull-request template.

## Method and maintenance

The assessment was produced by a parallel multi-agent audit: the criteria
were fetched from the canonical machine-readable registry, and three
independent auditors verified each group against the live repository and
GitHub API rather than against prior claims. Re-assess when the licensing
decision lands, when a release changes delivery mechanics, or when CI gates
change; update the entry at bestpractices.dev in the same increment.
